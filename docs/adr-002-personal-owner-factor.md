# ADR-002: персональный второй фактор владельца

Статус: Proposed. Реализован для проверки в отдельной ветке; фактическое подключение аккаунтов и перевод production — отдельный этап.
Дата: 2 ноября 2026, Europe/Minsk.

Контекст: общий OWNER_TOTP_SECRET не подходит двум независимым владельцам. STAFF-приглашение не должно повышать роль до OWNER. Нужен серверный путь назначения и восстановления без публичного bootstrap.

Решение: `owner_credentials` с AES-256-GCM ciphertext под существующим DATA_KEY, один отдельный Base32-секрет на пользователя. CLI требует два одинаковых числовых ID, факт подписанного Telegram-входа (`telegram_verified_at`), личный секрет и текущий код через защищённое окружение. Для добавления владельца нужны `--add-owner` и ID уже существующего владельца `--authorizing-telegram-id`. Серверный оператор является доверенной стороной; ID инициатора — запись для аудита, не удалённая авторизация. Роль OWNER не выдаётся HTTP-приглашением. Удаление OWNER через HTTP по-прежнему запрещено, включая последнего.

Проверка фактора: свежий Telegram-вход моложе 5 минут, текущая роль OWNER, персональный TOTP с окном ±30 секунд. Код потребляется атомарно под блокировкой строки; тот же или более старый шаг нельзя использовать в другой сессии. Успех даёт только этой сессии step-up на 5 минут, ограниченный также свежестью Telegram-входа. Повторы команд внутри этой сессии сохраняют идемпотентность. Ротация через `--enroll-totp --confirm-factor-reset` отзывает все сессии и сохраняет аудит, секрет и код в аудит не попадают. Публичного восстановления нет.

Миграция: 007 добавляет таблицу/поля и заполняет факт входа только по существующим auth_replays. Не копирует общий секрет, не создаёт новых владельцев. После обновления владельцы без персонального фактора могут читать данные, но их production-команды заблокированы до подключения через CLI. Общий OWNER_TOTP_SECRET больше не используется. Не передавать его второму человеку. DATA_KEY сохраняется при обновлении.

Совместимость и откат: схема добавочная, история и роли сохранены. Старый код не знает персональных факторов и снова использовал бы общий секрет; поэтому откат к старой аутентификации на рабочем магазине запрещён без отдельной оценки и закрытия служебного доступа. Предпочтителен исправляющий релиз. Копия БД не создаётся автоматически.

Альтернативы: общий секрет отклонён; HTTP enrollment/recovery с одноразовыми кодами требует дополнительного канала доверия и увеличивает объём текущей задачи. WebAuthn требует отдельной проверки Telegram webview. Персональный TOTP через доверенный сервер укладывается в текущий стек и даёт независимость владельцев.
