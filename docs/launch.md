# Подготовка и запуск на одном VPS

Эта инструкция подготовлена для отдельного согласованного размещения. Команды публикации в текущей разработке не выполнялись. Не включайте реальных покупателей до завершения проверки магазина и согласованного теста.

Магазин — секонд-хенд «Лучок» в Минске. Бот — [@luchok_secondhand_bot](https://t.me/luchok_secondhand_bot), `BOT_USERNAME=luchok_secondhand_bot`. Для подключения нужен токен этого бота; один username не даёт доступа к Telegram API. Аккаунт поддержки для личной переписки указывается отдельно в настройках магазина (`telegramUsername`); username бота не подставляется вместо него. Подтверждены адрес: Минск, ул. Жореса Алфёрова, 9 и ежедневные часы 10:00–20:00. Вход и помещение не уточнялись.

## 1. Данные владельца и счёт

- Получить итоговый счёт белорусского VPS: аренда, обязательный IP, налоги и дополнительные услуги вместе не более 50 BYN/месяц. Годовая цена со скидкой не равна цене помесячной оплаты.
- Домен приобретается отдельно. Указать человека, который будет обслуживать ОС и обновления.
- Заполнить фактические реквизиты продавца, адрес, часы и исключения, телефон и Telegram username поддержки. Утвердить документы о брони, товарах/возвратах и ПД с учётом ассортимента секонд-хенда. Непроверенные правовые сроки не подставлять.
- Для Белпочты и Европочты отдельно подтвердить договор, реквизиты/дату проверки, наложенный платёж, плательщика услуг, упаковку/комиссии и порядок возврата. Не включать способ одной галочкой без этих сведений.

Часть юридических первоисточников в исходной спецификации оставалась недоступной. Техническая разработка не заменяет проверку действующей редакции перед публикацией условий.

## 2. Диск и ресурсы

Исходный кандидат — 1 vCPU / 2 GB RAM; соответствие рабочей нагрузке проверяется замером. Считайте БД, ОС/образы, исходные очищенные фото, четыре варианта, свободное место под обработку и рост. Например 5 000 × 5 × 2 MB ≈ 50 GB только исходников: диск 40 GB не вместит этот набор. Начальный объём рассчитывайте по фактическому среднему размеру файла и числу вещей.

Для пробного размещения на 1 vCPU / 1 GB RAM production Compose ограничивает пулы API/worker до 5/2 соединений; PostgreSQL: `max_connections=30`, `shared_buffers=64MB`, `work_mem=2MB`, `maintenance_work_mem=16MB` (также наследуется autovacuum). Это настройки отдельных потребителей памяти, а не общий лимит RAM. Соответствие всего стека 1 GB нужно проверить на целевом сервере, включая загрузку фото. Изменение параметров PostgreSQL требует перезапуска БД; публикацию выполняют в согласованное окно.

Вне Compose пул по умолчанию равен 5; `PG_POOL_MAX` задаёт целое число 1–30 (для отдельного worker — 2). Таймауты, транзакции и повторы сохранены. Worker проверяет сроки, outbox и удаление временных контактов каждые 30 секунд после завершения цикла; очистка файлов уже ограничена одним запуском в час. Heartbeat остаётся в `jobs`, успешный цикл больше не добавляет `worker.tick` в аудит. Статика остаётся в общем образе Fastify: отдельная доставка сборки в Caddy для этого объёма не оправдана.

Условия для диска: постоянный локальный том, свободное место и контроль его расхода. При недостатке места остановите загрузки и разберите причину; не удаляйте фото из истории активных обращений или споров. Раздел «Управление → Операции» показывает состояние доступного диска и очередей.

## 3. Секреты и домен

На целевом сервере создайте `infra/.env` из примера, права файла `600`. Пароли и ключи храните только там/в защищённом механизме развёртывания. Не присылайте их в чат и не добавляйте в исходники. Нужны:

- `POSTGRES_PASSWORD` — случайный пароль БД; символы должны быть корректно кодированы для URI (проще длинная hex-строка).
- `DATA_KEY` — 32 случайных байта hex, неизменный при обновлениях; без него сохранённые контактные снимки не расшифровать.
- `BOT_TOKEN`, `WEBHOOK_SECRET` — секреты Telegram.
- Персональный TOTP каждого владельца — через защищённое окружение одноразового CLI. Общий `OWNER_TOTP_SECRET` больше не используется; не передавайте его второму человеку.
- `APP_ORIGIN=https://ваш-домен`, `DOMAIN`, `ACME_EMAIL`, `APP_MODE=production`, `NODE_ENV=production`, `BOT_DELIVERY_MODE=live`.

Caddy получает HTTPS-сертификат после правильной DNS-записи и доступности 80/443. PostgreSQL наружу не публикуется. Доступ SSH ограничьте штатными средствами ОС. Production с `APP_MODE=local` или без обязательной конфигурации должен завершиться ошибкой.

## 4. Сборка и первый запуск

Из корня проекта после отдельного согласования:

```bash
docker compose --env-file infra/.env -f infra/compose.yaml build
docker compose --env-file infra/.env -f infra/compose.yaml up -d
docker compose --env-file infra/.env -f infra/compose.yaml ps
```

Одноразовый сервис `migrate` ждёт готовую БД и применяет последовательные миграции. API/worker стартуют только после его успешного завершения. Версия образа `APP_IMAGE` должна быть сохранена для возможного отката приложения.

Проверить `https://домен/health/ready`, `healthy` у worker (heartbeat `maintenance` моложе 120 секунд), доступность витрины и закрытое оформление до настройки. Не включать seed. Не выполнять `down -v`: это удаляет рабочие тома. Новая пустая БД не считается восстановленным магазином.

## 5. Владелец и Telegram

Сначала покупательский вход нужного аккаунта должен создать пользователя через проверенное Telegram initData. Сверьте цифровой Telegram ID владельца независимо. Назначение первого владельца выполняется в контейнере на сервере:

```bash
docker compose --env-file infra/.env -f infra/compose.yaml exec api node dist-server/scripts/owner.js --telegram-id ID --confirm-telegram-id ID
```

Замените оба `ID` одним проверенным числовым ID. CLI первого владельца откажет, если OWNER уже есть, ID расходятся, пользователь не прошёл настоящий Telegram-вход или личный фактор не подтверждён. Для второго OWNER и миграции фактора см. раздел 9 ниже. Существующие сессии отзываются; переоткройте Mini App.

План настройки бота без обращения к Telegram:

```bash
docker compose --env-file infra/.env -f infra/compose.yaml exec api node dist-server/scripts/telegram.js
```

Только после отдельного согласования рабочего бота и домена:

```bash
docker compose --env-file infra/.env -f infra/compose.yaml exec api node dist-server/scripts/telegram.js --apply --confirm-origin https://ваш-домен
```

Скрипт ставит webhook с секретным заголовком и menu Web App button, не стирает ожидающие update. Main Mini App в профиле задаётся через BotFather. Токен/секрет скрипт не печатает. Повторно проверьте реальную настройку, если ответ потерян.

## 6. Настройка магазина и проверка

Владелец заполняет управление, календарь, реквизиты/документы и условия каждой почты. Добавляет реальные вещи собственными фотографиями через редактор. Минимум для технической проверки — несколько отдельно учтённых тестовых вещей; заполнять весь каталог для завершения разработки не требуется.

Проверить с явно согласованными участниками: самовывоз с отказом от строки; обе почты, трек отдельно от сдачи; отмена после ярлыка; получение/невостребованное; возврат и осмотр. Никаких реальных сообщений, выдач или посылок случайным людям. Telegram iOS и Android проверяются отдельно по T24 в `verification.md`.

## 7. Обновление и откат приложения

Сохраните номер текущего образа и список миграций. Проверьте совместимость новой миграции с предыдущим кодом: деструктивные изменения нельзя откатывать вслепую. Остановите приём новых оформлений настройкой магазина на время вмешательства в несовместимую схему; действующие обращения не удаляйте.

Соберите новую версию, выполните миграции, затем обновите API/worker. Проверьте health, журнал ошибок, очередь проблем и незавершённые операции. Возврат к прежнему `APP_IMAGE` с перезапуском API/worker допустим только при совместимой схеме. Это **откат кода**, не восстановление изменённой/утраченной БД.

## 8. Обычный перезапуск и потеря диска

Обычный restart на прежнем диске сохраняет тома: PostgreSQL восстанавливает согласованность транзакций, worker догоняет сроки и outbox. После перезапуска сверьте незавершённую выдачу/кассовую продажу по факту; такие вещи нельзя автоматически выставить снова.

При недоступной БД оформление/выдача закрыты ошибкой, нельзя принимать скрытые офлайн-команды. При потере диска восстановление возможно только из проверенной внешней копии (раздел 10). При отсутствии такой копии выключите оформление; повторная загрузка каталога и физическая инвентаризация обязательны до публикации. Наличие скрипта не подтверждает резервирование: нужны успешный запуск на VPS, внешняя копия и проверка восстановления.

Контроль: `docker compose ... ps`, health endpoint, защищённая очередь проблем/outbox, свободный диск. Логи ограничены размером, не должны содержать токены, контактные данные и необработанный initData. При разборе не копируйте секреты в публичные сообщения.


## 9. Новые сведения и два владельца

На **новой неизменённой базе** после миграций выполнить `npm run store:init -- --confirm-new-store` (в контейнере — `node dist-server/scripts/store-initial.js --confirm-new-store`). Скрипт один раз заполнит подтверждённый адрес, семь дней 10–20, текст «О магазине», тестовый телефон и явно обозначенные черновики. Оформления/обе почты останутся выключены; существующая рабочая база не перезаписывается. Изменения владельца вносить через управление.

В защищённом сеансе сервера подготовить **разный** личный секрет каждого владельца и подключить к его аутентификатору. CLI получает `OWNER_PERSONAL_TOTP_SECRET` и `OWNER_PERSONAL_TOTP_CODE` только через защищённое окружение процесса. Не записывать в Git, аргументы, логи, историю команд и сообщения чата. Одноразовые переменные после операции удалить из окружения. Не добавлять эти значения в общий env API/worker.

Первый владелец: обычный `owner.js --telegram-id ID --confirm-telegram-id ID`. Второй:

```bash
node dist-server/scripts/owner.js --add-owner --telegram-id SECOND_ID --confirm-telegram-id SECOND_ID --authorizing-telegram-id FIRST_ID
```

Оба аккаунта предварительно проходят подписанный Telegram-вход. `SECOND_ID` вводится дважды, `FIRST_ID` — ID уже назначенного владельца. Доверенный оператор сервера сверяет личности отдельно. Для существующего владельца после миграции 007: `--enroll-totp --telegram-id ID --confirm-telegram-id ID`. Для аварийной замены уже подключённого фактора дополнительно нужен `--confirm-factor-reset`; сессии отзываются. Общего секрета/fallback нет. При отсутствии фактора production-команды владельца закрыты; после подключения дождаться следующего кода и заново войти. Модель и пределы отката — ADR-002.

Оба владельца должны разрешить сообщения бота; это отдельная настройка, CLI не выдаёт такое согласие. Проверить по одному уведомлению о новой брони/доставке и важной проблеме каждому, а также доступ в служебную карточку по ссылке.

Новые тексты сначала сохраняются как DRAFT при закрытом оформлении. После проверки отдельным сохранением утвердить APPROVED. Изменение документа сбрасывает подтверждение в интерфейсе; сервер запрещает наследовать старое утверждение. Тестовый телефон (включая известный номер +375337777777 даже при снятом флаге) не открывает реальные оформления.

Целевой старт: самовывоз + Европочта после реального договора/проверки условий. Белпочту не включать. Обоснование — shipping-research-2026-11-02.md. Кандидат VPS и полная проверенная конфигурация цены — hosting-research-2026-11-02.md. Расходы, реальный HTTPS и переключение бота остаются отдельными действиями по конкретному адресу.

## 10. Резервные копии

Для запуска на Micro используйте существующий стек в `/opt/luchok`, без отдельного платного сервиса. `infra/backup.sh` создаёт потоковые зашифрованные age-копии PostgreSQL (`pg_dump -Fc`), всего media-тома и `infra/.env`/Compose/Caddyfile. Ключ `DATA_KEY` входит в зашифрованную конфигурацию: без него контакты восстановить нельзя. Открытых промежуточных архивов нет. Два полных последних снимка хранятся в `/var/backups/luchok` с правами 700; старые удаляются только после успешного создания следующего. Скрипт проверяет запас места (не менее 1 GiB сверх оценки новой копии), исключает параллельный запуск и возобновляет остановленные сервисы при обычной ошибке/сигнале.

На время согласованного снимка API и worker останавливаются; Caddy возвращает временную недоступность. Это обеспечивает согласованность БД и фото при изменении/очистке файлов. Автозапуск назначен на 04:00 Europe/Minsk; пропущенное время после включения сервера не догоняется посреди дня. Перед включением таймера замерьте длительность окна. Зависший процесс, аварийная остановка питания или SIGKILL требуют проверки оператором; таймер не заменяет мониторинг.

Секретный ключ age создаётся на компьютере владельца штатным `age-keygen` и хранится в защищённом месте отдельно от VPS. Не передавайте его в чат, Git или на сервер. На VPS копируется только получатель `age1...` в `/etc/luchok-backup-recipients.txt`. Установить `age` из штатного репозитория ОС. После ручного успешного снимка и проверки восстановления:

```bash
sudo bash /opt/luchok/infra/backup.sh
sudo install -m 644 /opt/luchok/infra/luchok-backup.service /etc/systemd/system/
sudo install -m 644 /opt/luchok/infra/luchok-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now luchok-backup.timer
sudo systemctl list-timers luchok-backup.timer
```

Контроль: `systemctl status luchok-backup.service`, `journalctl -u luchok-backup.service`, дата последнего полного каталога, свободное место, health API/worker после запуска. Нет места — копия не создаётся; старые снимки не стираются ради попытки. На диске 15 GB дополнительно учитывать два снимка и место для третьего; допустимый каталог определяется фактическим объёмом фотографий. Еженедельные копии провайдера учитываются только после проверки включения в оплаченный тариф и доступного восстановления.

Обязательно копировать завершённые каталоги с `SHA256SUMS` по SSH на компьютер владельца или уже имеющийся независимый носитель и контролировать свежесть. До настройки такого копирования потеря VPS уничтожит и локальные снимки. Дополнительное платное хранилище не подключать без разрешения. Ориентир ежедневного задания — до суток потери данных только при ежедневном успешном внешнем копировании; RTO определяется фактическим восстановлением.

Проверка восстановления — на отдельной пустой БД `luchok_restore_test` и отдельном каталоге, без запуска рабочего бота/worker, без подключения к production. Для PostgreSQL использовать версию не старше источника. Проверить контрольные суммы, расшифровать и восстановить dump через `pg_restore --exit-on-error --no-owner --no-acl`, распаковать фото и конфигурацию в закрытый каталог. Пример для уже настроенного безопасного подключения к тестовой БД:

```bash
sha256sum -c SHA256SUMS
set -o pipefail
age -d -i /secure/owner-age-key.txt database.dump.age |
  pg_restore --exit-on-error --no-owner --no-acl -d luchok_restore_test
mkdir -m 700 restore-media restore-config
age -d -i /secure/owner-age-key.txt media.tar.age | tar -xf - -C restore-media
age -d -i /secure/owner-age-key.txt configuration.tar.age | tar -xf - -C restore-config
```

Сверить количество вещей/заказов/claims/outbox и наличие всех фото, проверить расшифровку данных восстановленным `DATA_KEY`, открытие фото и сохранность броней. Секреты из конфигурации не печатать. Только после этого копию считать проверенной. Реальное аварийное восстановление требует отдельного окна, закрытого оформления и сверки физических остатков; не восстанавливать поверх работающей БД.
